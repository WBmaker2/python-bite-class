## 1. Linear 연동 결과

Linear 플러그인으로 팀·프로젝트·관련 이슈를 조회했다.

- 조회 가능한 팀: `Wbmaker01`.
- 프로젝트 목록: 0개.
- `파이썬` 검색 결과: 이슈 0개. 다른 제목의 모든 이슈가 없다는 뜻은 아님.
- 따라서 기존 프로젝트나 중복 이슈에 연결하지 못했다. 아래 G7 번호는 이 보고서의 초안 번호이며 실제 Linear 이슈 번호가 아니다.
- 검토 요청 범위에 따라 프로젝트/이슈 생성, 담당자 지정 등의 외부 변경은 하지 않았다.

## 3. 유지하면 좋은 점

- 읽기/실행/도전/선택 참고의 구분과 세부 목차가 있다.
- 핵심 용어, 예시, 도전 순서, 힌트가 같은 단계에 모여 있다.
- 브라우저에서 바로 Python을 실행하고 문법 오류를 한국어로 안내한다.
- 무한 반복을 중단한 다음 정상 코드로 다시 실행할 수 있다.
- 6.2에서 `score += 7`로 바꾸어 실행하면 `15`가 출력되고 정상 통과한다.

### G7-01 — 실행 결과와 실행한 코드 연결

- 재현: 2.2 시작 코드를 실행한다. 출력이 나온 뒤 이름을 추가하거나 문법이 잘못된 코드로 수정한다. 재실행하지 않는다.
- 실제: 출력은 이전 `오늘 배우는 언어: Python 3`인데 성공 표시와 완료 버튼이 활성화된다. 문법이 잘못된 편집 내용에서도 확인했다.
- 영향: 학생이 실제로 실행하지 않은 코드를 정답으로 믿고 다음 단계로 넘어간다.
- 원인: `src/features/playground/PlaygroundPanel.tsx:18`에서 이전 outputs를 현재 code와 결합해 재평가한다. 편집 시 실행 결과의 유효성을 무효화하지 않는다.
- 제안: 실행한 코드 스냅샷/runId와 결과를 연결한다. 편집하면 이전 출력을 참고용으로 유지하되 “코드가 바뀌었어요. 다시 실행해 주세요”를 표시하고 새 완료 판정을 막는다.
- 수용 기준: 실행 후 수정만으로는 통과하지 않는다. 잘못된 코드도 마찬가지다. 최신 코드 재실행 성공 시만 활성화된다. 실행 중 편집·단계 이동·초기화에도 다른 실행의 결과가 섞이지 않는다.

### G7-02 — 학습 목표와 무관한 변경의 거짓 성공

- 공개 재현: 11.8에서 전체 코드를 `print("다시 시작")`으로 바꾸고 실행한다.
- 실제: “나의 준비물과 수량으로 프로젝트 결과를 바꿨어요.”라고 성공 처리된다. 준비물·함수·조건·반복은 모두 없어진 상태다.
- 로컬 추가 검사: 6.2, 7.1, 8.7, 11.8 시작 코드 뒤에 `unused = 1`만 붙이고 원래 출력을 전달해도 판정 함수가 통과시킨다.
- 원인: `src/features/playground/challengeCheck.ts`의 changed는 출력이 비어 있지 않고 소스가 달라졌으면 만족한다.
- 제안: 단원별 관찰 목표를 정의한다. 예를 들어 11.8은 재고/필요량과 출력 목록의 관계, 7.1은 다른 분기의 실행을 확인한다. 정확한 소스 문자열 하나만 허용하지 말고, 학습 목표에 해당하는 행동과 데이터 결과를 함께 확인한다.
- 수용 기준: 무관한 변수 추가·무관한 출력은 실패한다. 동등한 계산 결과가 나오는 다른 숫자, 다른 유효한 이름/분야 등 복수 정답은 계속 인정한다. 명시한 과제 목표와 성공 메시지가 일치한다.

### G7-03 — 5.6의 출력 형식 편향

- 재현: 기존 두 줄 아래 `print(type(3.14))`를 추가하고 실행한다.
- 실제: `int`, `str`, `<class 'float'>`가 올바르게 출력되지만 실패한다. `print(type(3.14).__name__)`는 통과한다.
- 원인: `src/content/chapter5.ts:9`는 독립된 float/bool 문자열만 정규식으로 허용한다. 힌트는 `type(3.14)` 또는 `type(True)`를 한 줄 추가하라고 안내한다.
- 제안: 이번 목표가 자료형 관찰이므로 두 출력 형식을 인정한다. 힌트에는 출력까지 포함한 완전한 한 줄을 제공하고, .__name__은 이름만 꺼내는 선택 설명으로 구분한다.
- 수용 기준: float/bool의 두 표기 모두 통과한다. int/str만 추가한 경우는 실패한다. 편집 후 미실행은 통과하지 않는다.

### G7-04 — 본문 예제와 실습창의 역할 구분

- 서로 다른 예제/시작 코드가 있는 단계: 2.2, 2.3, 5.6, 7.2, 8.6, 8.8, 8.9, 9.1, 9.2, 10.6, 11.3, 11.8.
- 차이가 있다는 사실 자체가 결함은 아니다. 그러나 어느 코드를 실행하라는 안내인지 구분되지 않는 곳은 개선이 필요하다.
- 공개 재현: 9.1 본문은 sqrt와 fabs를 실행해 두 결과를 관찰하라고 한다. 시작 코드는 `print(round(math.sqrt(25)))`뿐이어서 실행 결과는 `5` 한 줄이다.
- 제안: “설명용 작은 예제”와 “오른쪽에서 실행할 코드”를 명확히 나눈다. 시작 코드 기준 예상 출력은 실제와 일치시킨다. 예제 가져오기를 제공한다면 현재 코드 덮어쓰기 확인/되돌리기도 제공한다.
- 수용 기준: 12단계마다 설명용/실습용 역할을 검토한다. 복사하지 않고 실행 버튼만 눌렀을 때의 결과 안내가 정확하다. fabs의 0 입력은 0임을 설명해 “항상 양수”라는 오해를 막는다.

### G7-05 — 지시와 힌트의 모순 교정

- 7.4: 힌트는 “두 4를 7로”라고 하지만 시작 코드에 4는 `if number == 4` 한 곳뿐이다. print는 number를 출력한다. `src/content/chapter7.ts:7`.
- 2.2: 도전은 Python 3를 유지하라는데 관찰 안내는 language의 오른쪽 글자를 바꾸라고 한다. `src/content/lessonGuides.ts:24`.
- 11.5: 부족 목록 missing에 준비 완료 물건을 추가하라고 하면서 힌트는 반복문 아래 완료 print 한 줄을 추가하라고 한다. 그대로 모두 따르면 같은 물건이 준비 필요/완료로 중복 안내될 수 있다. `src/content/chapter11.ts:8`.
- 제안: 7.4는 조건의 숫자 한 곳만 수정하게 한다. 2.2는 출력에 이름 추가로 통일한다. 11.5는 부족 목록과 준비 완료 목록/판정을 분리한다.
- 수용 기준: 힌트가 가리키는 위치가 실제 코드에 존재한다. 과제·힌트·정답 예시를 순서대로 따라 하면 목표 결과가 나온다. 교사 설명 없이 따라갈 수 있는 완전한 예시를 검수한다.

### G7-06 — 모두 준비됐을 때의 성공 안내

- 재현: 11.8에서 supplies 수량을 needed 이상으로 맞춘다. 함수와 for 문은 유지한다.
- 실제: 실행은 완료되지만 출력이 비고 “아직 목표 결과와 달라요”가 표시된다.
- 해석: 과제가 부족 목록을 만들도록 요구하기는 한다. 다만 실제 문제 해결에서는 부족품이 0개인 것도 정상 상태다. 빈 화면을 오류처럼 보이게 하지 않는 설계가 필요하다.
- 제안: 부족품이 없으면 “모두 준비됐어요!”를 출력하는 분기를 가르친다. 또는 이 단계에서 부족품을 적어도 하나 남겨야 한다면 과제·실패 안내에 그 조건을 명시한다.
- 수용 기준: 부족 0/1/여러 개, 재고가 정확히 같은 경우, 재고 목록에 없는 항목의 기대 동작과 판정을 정의하고 검증한다.

### G7-07 — 개념 순서·정의·확인 과제 재구성

- 8.2 코드가 return을 사용하지만 해당 단계 용어는 지역 변수/범위이고 return의 본격 학습은 8.7이다.
- 8.6은 *매개변수, 튜플, *호출, sum, len을 함께 사용한다. 튜플 단원은 뒤의 10단원에 있어 인지 부담이 높다.
- 8.8 문서 문자열 과제는 함수 인수 숫자만 바꾸므로 문서 문자열을 이해했는지 확인하지 못한다.
- 8.3 본문은 global을 “밖 변수를 안에서 바꾸는” 표시로 설명하지만 용어 정의는 “사용”이라고 되어 있다. 단순 읽기와 재할당을 구분해야 한다.
- 11.8 최종 통합 과제에서 새 리스트 컴프리헨션까지 도입한다. 11.4의 풀어 쓴 반복문을 재사용하고 축약형은 선택 참고로 낮추는 편이 입문자에게 적절하다.
- 수용 기준: 새 구문은 최초 실행 전에 값의 흐름 예시로 소개한다. return을 먼저 배우게 하거나 8.2에 필요한 짧은 설명을 넣는다. 문서 문자열은 설명 읽기/수정 과제로 확인한다. 선택 심화는 필수 진도를 막지 않는다.

### G7-08 — 초기 반복 통합과 단원별 목표

- 3.3·4.3 등의 출력 내용 바꾸기와 4.4·4.5·5.3의 단순 문자열 수정이 반복된다. 다른 개념을 복습하는 반복은 남기되 각 과제가 확인하는 능력이 달라야 한다.
- 제안: 3단원은 실행/중지/초기화와 저장 범위를 익히는 짧은 안내로 정리한다. 4단원은 출력 순서 예상→실행→일부러 낸 오류 복구로 차별화한다. 5단원부터 변수·값의 종류·표현 방법을 집중 학습한다.
- 전체 문장을 한꺼번에 길게 늘리지 말고 “한 문장 개념 → 2~4줄 예제 → 결과 예상 → 한 가지 변경 → 왜 바뀌었는지” 순서로 안내한다. 추가 설명은 펼쳐 보기로 제공한다.
- 수용 기준: 각 필수 실습마다 독립된 학습 목표 하나를 명시한다. 같은 문자열 치환만 확인하는 단계는 통합/읽기 전환한다. 통합 시 기존 진도 ID 이전 정책을 포함한다.

### G7-09 — 실행 준비와 오류 복구 안내

- 확인된 장점: 문법 오류의 한국어 설명, 무한 반복 5초 중단, 이후 재실행이 작동한다.
- 코드상 위험: `src/hooks/usePythonRunner.ts:33` 부근의 5초 타이머가 런타임 로딩까지 포함한다. 느린 네트워크의 첫 로딩에도 반복문을 확인하라는 오해의 안내가 나갈 수 있다. 느린 네트워크 재현은 이번에 하지 않았다.
- 공개 오류 화면에는 Python 내부 파일 경로와 긴 traceback이 그대로 표시된다.
- 제안: 준비 중 시간 제한과 실제 코드 실행 제한을 분리하고, CDN/네트워크 실패에는 재시도 안내를 준다. 학생에게는 자신의 코드 줄과 수정 힌트를 먼저, 내부 traceback은 상세 보기로 제공한다.
- 수용 기준: 느린 첫 로딩/네트워크 실패/문법 오류/무한 반복/출력 초과가 서로 다른 안내로 나타난다. 모든 경우 수정 후 재실행할 수 있다.

### G7-10 — 회귀 테스트를 학습 행동 중심으로

- 기존 테스트가 통과해도 G7-01~03이 재현됐다. 콘텐츠 속성 존재와 특정 체크 모드 검사만으로 의미적 정합성을 보장할 수 없다.
- 추가할 사례: 기본 실행 → 변경 → 재실행, 실행 후 미실행 변경, 동등한 복수 정답, 무관한 변경, 빈 정상 결과, 힌트 그대로 작성, 단계 이동 중 실행, 기존 진도 복원.
- 최소 수용 기준: G7-01~03은 UI 통합 테스트와 실제 브라우저 회귀 시나리오를 갖춘다. 각 도전에 정상 정답 2개 이상과 오답/무관한 변경 사례를 둔다. 예상 출력과 시작 코드를 자동 검증한다.
- 별도 후속 검증: 정확한 320/375/768px 시각 확인, 키보드 이동·편집기 탈출, 새로고침 저장, 저장소 거부, 느린 네트워크. VoiceOver는 제외한다.

## 6. 권장 실행 순서와 실제 학생 검증

1. G7-01~03: 판정 신뢰성부터 복구하고 회귀 테스트 추가.
2. G7-04~06: 본문·힌트·시작 코드·결과·판정의 모순 해소.
3. G7-07~09: 학습 순서/반복/오류 안내를 정리한 뒤 좁은 화면과 느린 환경 검증.
4. 실제 중1 입문 학생 3~5명에게 짧은 세션으로 검증. 한 사람이 69단계를 한 번에 완주하게 하기보다 수준별로 나누어 관찰.

실제 학생 테스트 제안은 아직 수행하지 않았다. 학생에게 정답을 먼저 알려주지 않고 “지금 무엇을 하려고 하나요?”, “어떤 결과가 나올까요?”, “안 될 때 무엇을 해보겠어요?”를 묻는다. 이름 대신 익명 식별자로 도움 요청 횟수, 힌트 사용, 잘못된 완료 시도, 오류 후 복구 여부를 기록한다.

- 첫 세션: 시작 안내 → 첫 실행 → 문장 변경 → 오류 복구.
- 선수 학습 후 세션: 5.6 자료형 → 6.2 할당 연산 → 7.4 break.
- 함수/자료 구조 학습 후 세션: 9.1 모듈 → 11.5 안내 → 11.8 정상/부족 상황 비교.
- 성공 기준은 사전에 정하되, 이번 AI 테스트 결과로 학생 성공률이나 학습 시간을 추정하지 않는다.

초기 감사 시점에는 이 보고서만 새로 작성했고 앱 소스 수정은 보류했다. 이후 사용자의 수정 요청에 따라 아래 8절의 소스 수정과 회귀 검증을 추가했으며, 기존 작업 파일은 보존했다. 커밋·푸시·배포와 Linear 이슈 등록은 수행하지 않았다. ego-browser 스킬에 따라 사용자와 분리된 테스트 공간을 사용했다. Visualize 스킬은 제공 목록에서 확인되지 않아 표로 우선순위와 범위를 정리했다.
