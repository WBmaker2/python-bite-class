# Firebase 과제 제출·교사 보고서 기능 검토

검토일: 2026-09-10
상태: 구현 전 검토. 앱 코드·Firebase 설정·배포 변경 없음.

## 결론

현재 React/Vite 앱에 요청한 기능을 모두 추가할 수 있다. GitHub Pages 학습 화면을 유지하면서 Firebase Authentication, Cloud Firestore를 연결할 수 있다. 별도 서버 처리가 필요한 경우 Cloud Functions를 사용한다.

핵심 조건은 제출 전 로컬 저장 원칙, 학생별 기록 분리, 성공 판정과 답 코드의 연결, 서버에서 강제하는 교사 권한이다.

## 현재 코드에서 확인한 기반과 한계

- `src/components/AppHeader.tsx`: 상단 버튼을 추가할 위치가 있다.
- `src/hooks/useLearningProgress.ts`: 브라우저 공통 저장 키에 완료 단계와 단계별 최신 코드를 저장한다. 학생 프로필별 저장은 없다.
- `src/hooks/progressMigration.ts`: 저장 형식은 `completed`, `codeByLesson`이다. 이전 교육과정의 진도 이관 기능이 있다.
- `src/features/playground/PlaygroundPanel.tsx`: 실행과 도전 성공을 판정하지만 실행 코드·성공 여부·출력은 영구 저장하지 않는다.
- `src/content/types.ts`: 읽기, 실행, 도전, 선택 참고 단계가 구분된다.
- `src/content/chapters.ts`: 필수 진도 계산에서 선택 참고 단계를 제외한다.
- `package.json`: 현재 Firebase와 Excel/PDF 생성 라이브러리는 없다.

완료 후 코드를 수정해도 완료 이력은 남는다. 따라서 현재 자료만 제출하면 성공 당시 코드와 제출 코드가 다를 수 있다. 과거 실패 이력과 성공 당시 코드는 복원할 수 없으므로, 기존 진도는 보존하되 실행 근거가 없는 경우 '기존 완료 기록 / 검증 기록 없음'으로 구분한다.

## 학생 화면과 전송 경계

상단 배치: `[로그인] [과제 제출]`. 등록 후 로그인 위치에 학교·이름과 정보 변경/로그아웃 진입을 제공한다.

로그인은 학교와 이름 두 항목을 저장하는 로컬 프로필 등록이다. 본인 인증이나 기기 간 계정 복구를 의미하지 않는다.

권장 안내문:

> 소속(학교)과 이름은 이 브라우저에만 저장됩니다. ‘과제 제출’을 누르기 전에는 소속·이름·학습 진도·답 코드를 전송하지 않습니다. 제출하면 해당 정보가 교사의 Firebase 데이터베이스에 저장됩니다.

이미 제출한 자료는 로컬 로그아웃이나 진도 초기화로 서버에서 삭제되지 않는다는 점도 구분한다. 앱 파일과 Python 런타임 다운로드까지 네트워크 통신이 없다고 안내하지 않는다.

전송은 명시적 제출 동작에서만 시작한다. 입력·실행·페이지 이탈·로그아웃에 자동 제출을 연결하지 않는다. 제출 직전 학교·이름과 제출 범위를 확인할 수 있게 한다.

Firebase 익명 인증을 쓰면 학생 계정 입력 없이 요청 주체를 구분할 수 있다. 이 경우에도 첫 학생 인증 요청은 제출 시점까지 지연한다. 학교·이름을 인증 프로필, 분석 이벤트, 오류 로그에 포함하지 않는다.

익명 계정 생성에는 같은 IP에서 단시간에 가입하는 횟수 제한이 있으므로 학교 공용 회선에서 학급 동시 제출을 검증한다. 필요하면 공식 할당량 조정 또는 다른 제출 인증 방식을 선택한다.

제출 시점의 데이터를 고정하고 고유 제출 ID로 중복 요청을 처리한다. 서버 저장 확인 후에만 성공과 접수 시각을 표시한다. 오프라인 자동 전송 대기는 사용하지 않고, 실패하면 로컬 기록을 유지하며 수동 재시도를 안내한다. 응답만 유실된 경우에는 같은 제출 ID의 접수 여부를 확인한다.

## 학생 식별과 공용 기기

- 학교+이름은 동명이인이 있으므로 DB 기본 키로 쓰지 않는다.
- 로컬 프로필 ID와 인증 UID, 제출 ID를 구분한다. 인증 UID는 요청 주체이며 실명 확인 증거가 아니다.
- 프로필 변경 시 코드·진도·현재 단계를 함께 전환하고 이전 학생 자료를 자동으로 이어 붙이지 않는다.
- 기존 비로그인 기록은 어떤 프로필에 귀속할지 명시적으로 선택하는 최초 이관 절차가 필요하다.
- 공용 기기에서는 '이 기기에서 내 정보와 기록 지우기'를 제공하는 편이 좋다. 로컬 저장은 같은 브라우저의 다른 사용자를 차단하는 보안 수단이 아니다.
- 브라우저 데이터 삭제나 다른 기기 사용 시 기존 학생과 자동 연결되지 않는다. 기기 간 이어하기가 필요하면 추후 계정 또는 교사 발급 식별 수단이 필요하다.

## 제출 자료 권장 형식

| 구분 | 저장할 내용 |
|---|---|
| 제출 요약 | 제출 ID, 프로필 식별자, 요청 UID, 학교, 이름, 서버 접수 시각 |
| 교육과정 | 교육과정 버전, 단계 ID·제목·종류, 필수 단계 수 |
| 단계별 진도 | 완료 여부, 미시도/성공/실패/수정 후 미실행/검증 기록 없음 |
| 코드 | 제출 시점 코드, 마지막 실행 코드, 마지막 성공 코드(기록이 있을 때) |
| 실행 근거 | 마지막 판정, 판정 시각, 제한된 실행 결과·오류 요약 |

읽기 완료를 도전 성공으로 표시하지 않고, 미완료를 무조건 실패로 표시하지 않는다. 선택 참고는 별도 구분하며 필수 완료율 분모에 넣지 않는다. 실행 근거와 코드는 동일 실행 건으로 연결하고, 코드 변경 후에는 '수정 후 미실행'을 표시한다.

`submissions/{submissionId}`에 요약, 하위 단계 문서에 답안을 저장하는 구조를 권장한다. 크기·길이·허용 단계·데이터 형식을 제한하고, 모든 단계와 요약이 일관되게 저장된 제출만 교사에게 노출한다. 재제출은 새 제출본을 남겨 최신 제출과 이전 제출을 구분한다. 학생 목록에서 학교·이름만 같다고 제출을 자동 병합하지 않는다.

## 관리자 진입과 권한

히든 버튼은 구현 가능하지만 발견을 어렵게 하는 UI일 뿐 접근 제어가 아니다. URL 직접 접근과 Firestore 직접 요청도 교사 권한 없이는 거부해야 한다.

권장안은 히든 버튼 → Firebase 교사 계정 인증 → 교사로 등록된 UID 또는 서버에서 부여한 관리자 권한 확인 → 관리자 화면이다. 교사 역할은 학생이 수정할 수 없는 위치에서 관리한다.

`8582`는 교사 인증 후 보조 잠금으로 사용할 수 있다. 히든 버튼 + `8582`만 입력하는 흐름을 고수한다면 Cloud Functions 등 서버에서 비밀번호 검증, 시도 제한, 잠금, 만료 세션 발급을 구현해야 한다. 그래도 네 자리 공용 PIN은 추측·공유에 취약하므로 단독 보호 수단으로 권장하지 않는다. 브라우저 코드 또는 `VITE_` 환경 변수에 비밀번호나 관리자 비밀을 넣어서는 안 된다.

직접 Firestore 접근 방식은 Security Rules로 학생의 허용된 제출 생성만 열고 전체 조회·타인 조회·기존 제출 수정·삭제를 차단한다. 교사는 허용된 자료를 조회·내보내기할 수 있다. 서버 SDK 방식은 Security Rules를 우회하므로 서버 API에서 인증·권한·입력 검증을 직접 수행해야 한다. App Check는 보조 방어이며 교사 인증을 대체하지 않는다.

현재 판정은 학생 브라우저가 만든 학습 기록이다. DB 접근 통제로 조작된 성공 여부까지 진실로 증명할 수는 없다. 수업 진도 확인에는 활용할 수 있지만 엄격한 평가가 목적이면 별도 격리 실행 환경에서 서버 검증하는 추가 범위가 필요하다. 제출 코드를 일반 Functions 처리 안에서 그대로 실행하는 방식은 피한다.

## 관리자 화면과 보고서

- 학교·이름·접수일 검색, 학생별 최신 제출과 과거 제출 목록.
- 단계별 완료/실행 판정과 코드 상세 보기. 코드와 출력은 실행하지 않고 텍스트로 표시.
- Excel: 학생 요약, 단계별 결과, 제출 코드 시트. 개인별 또는 선택 학생 일괄 다운로드.
- PDF: 학교·이름·접수일, 전체/단원별 진도, 단계별 결과, 답 코드 부록.
- 보고서는 저장된 제출본을 기준으로 만들고 제출 ID와 교육과정 버전을 포함.
- Excel 셀은 사용자 문자열을 수식으로 해석하지 않도록 작성. 긴 코드는 길이 한도를 고려해 분리.
- PDF는 한글 글꼴과 코드 줄바꿈·페이지 분할을 검증. 인쇄 후 PDF 저장 방식과 직접 PDF 다운로드 방식 중 구현 범위를 구분.

교사 브라우저에서 보고서를 생성하면 별도 파일 서버 없이 내려받을 수 있다. 이 단계에서는 결과물 형식만 검토했으며 실제 Excel/PDF 파일은 만들지 않았다.

## 구현 순서와 검증 범위

1. 로컬 프로필과 진도 이관·분리, 실행별 판정/코드 기록 설계.
2. 제출 데이터 형식·재제출 정책·Firebase 권한 설계와 에뮬레이터 검증.
3. 제출 UI와 서버 저장 확인, 중복·오프라인·실패 대응.
4. 교사 인증, 제출 목록·진도표·코드 상세.
5. Excel/PDF 내보내기와 한글·긴 코드 검증.
6. 기존 학습 흐름과 모바일 상단, 중요 동작 강조, 업데이트 내역 반영.

검증에는 제출 전 학생 자료 미전송, 프로필 간 자료 혼합 방지, 성공 코드와 수정 코드 구분, 제출 전후 새로고침, 학생의 전체 조회 거부, 관리자 URL 우회 접근 거부, 부분 제출·중복 접수 방지, 보고서 내용 일치를 포함한다. VoiceOver 구현·검증은 제외한다.

이후 구현은 계획 확정 후 사용자 지침에 따라 gpt-5.6-luna가 담당한다. Firebase 프로젝트 연결 정보·교사 인증 방식·보관/삭제 운영 기준은 실제 연결 전에 정해야 한다. 서비스 계정 키나 교사 비밀번호를 소스 저장소에 넣지 않는다.

Cloud Functions를 실제 배포하려면 Blaze 요금제가 필요하다. 구체적인 비용은 제출 빈도, 단계별 문서 수, 조회·내보내기 범위와 보관량에 따라 달라지므로 무료 운영을 보장하지 않는다. 기존 Firebase 프로젝트의 요금제·권한·보안 규칙은 이번 검토에서 확인하지 않았다.
